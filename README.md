# CodeProof AI

[![CI](https://github.com/manners-parkpro/codeproof-ai/actions/workflows/ci.yml/badge.svg)](https://github.com/manners-parkpro/codeproof-ai/actions/workflows/ci.yml)

**코드리뷰 품질 측정 실험 플랫폼**
— 리뷰어를 비교하는 대신, **측정 방식이 결과를 얼마나 만드는지**를 측정한다.

> 🚧 개발 중 (v0.1.0). **정적분석기 경로는 지금 동작한다** — 모델 API 없이 돌려볼 수 있다.
> 설계 근거는 [docs/DESIGN.md](docs/DESIGN.md), 코드 작성 규칙은 [CLAUDE.md](CLAUDE.md).

```bash
uv sync
uv run codeproof doctor                       # 무엇이 준비됐는지
uv run codeproof measure --analyzers ruff     # 실제 측정. API 키 불필요
```

### 30초 요약 — 이 도구가 내는 숫자

증명 가능하게 안전한 코드에 Ruff 를 `--ruff-select ALL` 로 돌리고, **같은 지적을**
서로 다른 정답 정의로 채점했다. **지적은 하나도 바뀌지 않았다. 정의만 바꿨다.** [실측 · 60쌍]

| 채점자 | FP | 판정불가 | 정의 |
|---|---:|---:|---|
| `provable_safety` | **7** | 231 | 서면 안전 근거가 덮는 결함 주장만 FP |
| `injected_defect` | **238** | 0 | 결함 위치와 안 맞으면 전부 FP (Qodo 계열) |

**34배** [실측 · 60쌍]. 그리고 짝 채점도 같은 일이 일어난다 — **같은 도구, 같은 지적**인데
한 정의는 「거의 다 놓쳤다」(P-B 54), 다른 정의는 「거꾸로 찾았다」(P-R 46)로 판정한다 [실측 · 60쌍 · 결과 3].

🔴 **이 편차 자체도 손잡이의 함수다.** 위 숫자는 `--ruff-select ALL` 에서 잰
것이고, 보안 룰만 고르면(`--ruff-select S`) 두 정의가 **정확히 일치해 편차가
사라진다.** 편차의 정체가 「판정 불가로 둘 것을 오답으로 세느냐」이기 때문이다 —
보안 룰은 전부 근거 범위 안의 결함 주장이라 이견이 생길 자리가 없다.
한 줄로 확인한다: [docs/VERIFY.md](docs/VERIFY.md) 의 **손잡이 실험**.

숫자는 `uv run codeproof report` 가 만든 [docs/MEASUREMENTS.md](docs/MEASUREMENTS.md)
에 있다. 산문에 베껴 두면 반드시 낡기 때문이다.

> ⚠️ **현재 음성 표본은 발표 기준(목표 150건)에 못 미친다.** 도구가 실행마다 그렇게 경고한다.
> 지금 크기는 「측정 선택이 숫자를 움직인다」를 보이기에 충분하고,
> 「이 도구의 오탐률은 X% 다」를 말하려면 더 필요하다 — **다른 주장이고
> 다른 표본이 든다.**

### 리뷰어는 한 가지 개념이다

지적을 내는 것은 전부 리뷰어이고, **같은 하네스로 돌고 같은 채점을 받는다.**

| 층 | 예 | API 키 |
|---|---|---|
| `static` | Ruff · mypy | 불필요 |
| **`imported`** | **SARIF**(CodeQL · semgrep · Snyk · Trivy) · **bandit JSON** | **불필요** |
| **`agent`** | **Codex CLI · Claude Code 출력을 저장해 가져오기** | **불필요** |
| `model_api` | Anthropic · OpenAI SDK | 필요 |
| `human` | 사람 리뷰 — 기준선이자 상한 | 불필요 |

```bash
# SARIF 를 내는 도구
semgrep --sarif -o out/<sample_id>.json ...
uv run codeproof import --from out --name semgrep --identity "1.2.3"

# SARIF 를 안 내는 도구도 포맷 어댑터 하나면 된다
# [실측] bandit 은 SARIF 를 지원하지 않는다 - 「SARIF 면 다 된다」는 절반만 맞다
bandit -f json -o out/<sample_id>.json -r .
uv run codeproof import --from out --name bandit --format bandit --identity "1.8"

# 에이전트 CLI - 격리·모델 고정·기록은 실행기가 한다 (DESIGN §7.10)
uv run codeproof export --out agent-in   # --docstrings neutral: 모듈 docstring 의 기전 문장을 지운다 (DESIGN §7.10c)
./scripts/review-with-agent.sh codex agent-in codex-out --effort low --runs 8   # effort 는 필수 · 반복 횟수는 수집 전에 선언 (F8)
#   크레딧이 한정이면 --runs 를 1 → 2 → … → 8 로 한 칸씩 올려 이어 돈다 - 샘플마다 N회를 다 돌고 넘어가서 (CLAUDE A2b)
#   벤더 최상위가 scripts/agent-models.json 의 기준과 다르면 멈춘다 - 따라갈지는 사람이 정한다
uv run codeproof import --from codex-out --name codex-cli --kind agent
#   포맷·identity·effort 는 실행기가 남긴 RUN.json 에서 읽는다 - 손으로 준 값이 다르면 거부
#   다회 실행은 합집합 한 줄이 아니라 단일 실행 기대값 · k-임계로 나온다 - 회차가 모자란 샘플은 거부
uv run codeproof pack --from codex-out --out results/agent/codex-cli
#   생성물(docs/MEASUREMENTS.md)에 싣는 묶음 - RUN.json + findings.jsonl 두 파일 (raw/ 는 빼고).
#   report 가 풀어서 import 와 같은 경로로 재생한다. 회차가 모자란 실행은 묶지도 싣지도 않는다
#   회차가 고르지 않으면 --runs N 으로 앞 N회만 묶는다 - N 은 수집 전에 선언한 값 (DESIGN §7.10b)
#   묶은 샘플을 RUN.json 의 packed_samples 로 적는다 - 코퍼스가 자라도 그 샘플로만 재생한다 (§7.10)
```

⚠️ **`agent` 와 `model_api` 는 섞어서 집계하지 않는다.** 에이전트는 파일 탐색·다회 턴·
툴 사용이 가능해서 조건이 다르다. `ReviewerKind` 가 그 경계를 타입으로 표현하고,
리포트가 구분해서 말한다.

## 왜 만들었나 — 49라운드가 수렴하지 않았다

실무 Spring 프로덕션 레포(소스 2,800여 개)에서 Codex 와 Claude 를 매일 함께 쓴다.
`AGENTS.md` 와 `CLAUDE.md` 를 나란히 두고, 세션마다 재주입되는 규칙 정본
(`.claude/rules/always.md`, 497줄)과 가드 훅 10개로 빌드 그린 · 문서 정합 · 규칙 무결성을
**사람이 아니라 하네스가** 막게 해뒀다.

그 레포에서 PR 하나를 두고 **리뷰 봇과 49라운드**를 돌았다. 기록은 이렇다.

| 실측 | 값 |
|---|---:|
| 봇 인라인 지적 | **149건** |
| 그중 이 PR 의 산출물에 대한 것 | **7건 (4.7%)** |
| 나머지 | 도구에 대한 것 142건 (95%) |
| 「발생 근거」가 제시된 지적 | **0건** (기전 재현만 15건) |
| 그럼에도 반영한 수정 | **15건** |
| 내 방어가 다음 라운드 지적을 만든 횟수 | **2회** |
| 되돌리기 직전 파일의 주석·산문 비율 | **65%** |

**이 루프는 수렴하지 않았다.** 지적을 다 해소해서 끝난 게 아니라,
**리뷰 대상 표면을 제거해서** 끝났다 — 2,212행을 331행으로 되돌렸다.

각 수정은 **하나씩 보면 옳았고 전체로 보면 틀렸다.** 오지 않는 상황을 막으려고
팀이 읽는 파일의 복잡도를 8배로 올렸다 [실측]. 그 비용은 리뷰에 나타나지 않는다.

그리고 결정적인 한 줄:

> **`shellcheck` 가 깨끗해도 리뷰는 끝나지 않는다 — 층이 다르다.**
> `shellcheck` 는 한 자릿수를 찾았고 봇은 수십 배를 찾았다.
> 정적 분석기 통과를 「이제 깨끗하다」의 근거로 쓰지 않는다.

여기서 답할 수 없는 질문이 남았다.

> **저 149건 중 무엇이 맞았는가? 무엇을 기준으로 그렇게 말하는가?**
> **기준을 바꾸면 답이 바뀌지 않는가?**

이 프로젝트는 그 질문에 답하는 **측정 장치**다.

## 이 코드가 보여주는 작업 방식

벤치마크 결과보다 **어떻게 검증했는지**가 본체다.
실무에서 얻은 원칙을 이 레포에서는 **코드와 테스트로** 박았다 — 규약이 아니라 강제다.

### 1. 기억이 아니라 구조가 막는다

> "런타임은 정답 라벨을 보면 안 된다" 를 **규약으로 적지 않고 import 불가로 만든다.**

정답 라벨(`Defect`·`LabeledSample`)은 `eval/` 안에만 있고, 런타임 레이어는 `eval/` 을
import 할 수 없다. 레이어 그래프 테스트가 위반을 잡는다
([`tests/architecture/test_layering.py`](tests/architecture/test_layering.py)).

처음엔 타입 이름 금지 **목록**으로 관리했는데, 새 타입이 생기면 갱신을 잊는다.
목록을 버리고 의존 그래프 하나로 바꿨다.

### 2. 근거 없는 주장은 받지 않는다 — 그리고 그 한계도 적는다

decoy 는 "왜 안전한지" **서면 근거가 없으면 코퍼스에 들어가지 못한다.**
검증기가 길이·낱말 수·인과 연결어를 보고 거부한다(V3).
`"안전하다"` 를 스무 번 반복하면 탈락한다.

모델 출력 스키마도 `failure_mode` 를 **필수**로 요구한다 —
*"어떤 입력에서 무엇이 잘못되는가"* 를 말하지 못하면 지적이 아니다.

### 3. 판정 불가를 오답으로 접지 않는다

실무 규칙에 이런 게 있다 — 모든 사실 주장에 `[실측]`(직접 실행·조회) / `[소스]`(문서 인용) /
`[추정]` 중 하나를 붙이고, **라벨을 붙일 수 없으면 그건 제안이 아니라 「확인 중」이다.**
그리고 🔴 **`[실측]` 은 관측값에 붙지 관측의 「해석」에는 붙지 않는다** —
*「rc=0 이었다」는 실측, 「그러므로 존재한다」는 추정*. 실행은 진짜였는데
해석이 틀린 사례가 실측 2건 기록돼 있다.

같은 규율을 채점에 적용한 것이 `UNDECIDABLE` 이다.
이 분야 문헌이 정확히 여기서 틀렸다. "아무도 코멘트를 안 달았다"(**증거의 부재**)를
"틀렸다"로 채점해서, **사람이 놓친 진짜 버그를 False Positive 로 만들어버린다.**

여기서는 `UNDECIDABLE` 이 1급 판정이다. 안전 근거가 덮는 범위 밖의 지적은
FP 가 아니라 "판정할 수 없음"이고, Precision 분모에서 빠지며,
**판정불가율을 같이 보고**한다 — 그 값이 크면 그 채점자가 그 층을 못 재는 것이다.

### 4. 정적 분석기 통과를 「깨끗하다」로 읽지 않는다

실무에서 얻은 결론 — *「`shellcheck` 가 깨끗해도 리뷰는 끝나지 않는다. 층이 다르다」* —
을 이 레포가 실측으로 재현한다.

`D002` 에서 Ruff 는 **안전한 코드와 터지는 코드에 같은 판정**을 냈다(아래 결과 1).
패턴 매칭은 `shell=True` 를 보고, 그 커맨드에 외부 입력이 닿는지는 보지 않는다.
그래서 정적 분석기는 **기준선**이지 **정답**이 아니다 — 여러 채점 기준 중 하나로만 쓴다.

### 5. 숨은 손잡이를 전부 공개한다

같은 코드·같은 도구여도 아래를 바꾸면 숫자가 바뀐다. 전부 실행 매니페스트에 실린다.

| 손잡이 | 실측 효과 |
|---|---|
| Ruff 룰 선택 | FP **0 → 4** |
| 그룹핑 정책 | 출현율이 달라진다 |
| 채점 범위 여유 | 판정불가 → FP 로 넘어간다 |
| effort | 모델마다 기본값이 다르다 (Opus 5.5 `medium` / Sonnet 5 `high`) |
| 캐시 정책 | OpenAI 비용 최대 **90% 과소보고** |
| 프롬프트 문구 | 포맷만으로 최대 **76 포인트** |

기록하지 않은 손잡이는 재현 불가이고, **재현 불가는 실험이 아니다.**

### 6. 자기 채점을 하지 않는다

결함 탐지 정답은 **제3자 코퍼스**(c-CRAB · AACR-Bench)를 쓴다. 내가 만든 정답으로
내 도구를 채점하지 않는다.

채점에 LLM 판정자도 쓰지 않는다 — 자기선호 편향(판정자는 저-perplexity 텍스트를
선호하고, 자기 출력은 구조적으로 자기에게 저-perplexity다)이 Claude vs Codex 비교를
무효화하기 때문이다. 코드 도메인의 판정자 일치도는 전 도메인 최악이다(κ 0.159).
다만 D층 정답은 Claude 가 썼다 — 같은 패밀리의 편향은 판정자를 빼도 남는다 (「재지 못하는 것」 6).

### 7. AI 끼리 투표시키지 않는다

Claude 와 Codex 지적을 한 관측에 넣으면 둘 다 찾은 것이 `2/2` 로 보여서
**출현 빈도가 자기일관성이 아니라 교차모델 합의를 재게 된다.** 조용한 투표다.
`MixedReviewerError` 가 타입 수준에서 거부한다.

> 교차모델 합의는 이미 약한 대리지표로 반증됐다 — ρ 0.20–0.59,
> 프런티어 모델은 합의 ≥0.8 인 77% 구간에서 **48%가 오답**이었다.

## 선행연구를 뒤져보니 — 아무도 답하지 않았다

같은 질문이 학계에도 있었다. 그런데 답을 찾는 대신 이상한 걸 발견했다.
같은 과제, 비슷한 도구인데 **발표된 Precision 이 20배 차이 난다** [소스: 아래 표의 각 논문].

| 벤치마크 | Precision | 정답의 정의 |
|---|---:|---|
| CR-Bench | ~3.5% | 사람이 실제로 남긴 리뷰 코멘트와 일치 |
| SWRBench | 16.65% | 〃 (균형 코퍼스) |
| Martian | 76.2% | 리뷰 후 개발자가 **실제로 고친 것**과 일치 |
| Qodo | 79% | **주입한 결함**과 일치 |

차이의 원인은 모델이 아니다. **전부 "정답을 무엇으로 볼 것인가"** 다.

그리고 — **동일한 지적 집합을 여러 정답 정의에 통과시켜 그 편차를 발표한 사례가 없다.**

### 그래서 질문이 정해졌다

49라운드에서 답할 수 없었던 그 질문이, 학계에서도 빈칸이었다.

> **"보고된 품질 숫자 중 얼마가 모델의 것이고, 얼마가 측정 선택의 것인가?"**

```
                    ┌─ Grader A ─┐
Finding[] (고정) ───┼─ Grader B ─┼──→ 같은 지적, 다른 Precision
   ↑                ├─ Grader C ─┤              ↓
Claude / Codex      └─ Grader D ─┘      편차 = 측정의 기여분
```

모델 비교는 사라지지 않는다. 그 **위에 축이 하나 더 얹힌다.**

이게 허황된 걱정이 아닌 이유 — 프롬프트 **포맷만** 바꿔도 정확도가 최대
**76 포인트** 움직인다는 게 이미 측정돼 있다
([Sclar et al.](https://arxiv.org/abs/2310.11324)). 측정 설정의 기여분이 모델 차이를
압도할 수 있다는 건 알려진 사실이고, 코드리뷰에서는 아직 아무도 재지 않았다.

## 핵심 기여 3가지

### 1. 채점 기준 편차 측정

같은 지적을 여러 정답 정의로 채점하고 **편차 자체를 보고한다.**
새 데이터셋이 필요 없고, 모든 벤더 주장을 즉시 재해석 가능하게 만든다.
**지금 동작한다** — 같은 지적 44건의 FP 가 정의에 따라 18~44 로 갈린다(아래 결과 2).

### 2. 정직한 False Positive

기존 문헌의 FP 율은 전부 **"틀림"이 아니라 "과거 리뷰어와의 불일치"** 를 재고 있다.

"Clean PR" 이란 *아무도 코멘트를 안 달았다*는 뜻이다.
**증거의 부재지, 부재의 증거가 아니다.**
사람 리뷰어가 놓친 진짜 버그를 모델이 잡으면 → **FP 로 오채점된다.**

이 프로젝트는 **"버그처럼 생겼지만 증명 가능하게 안전한"** 코드를 한 쌍씩 쓰고,
**안전한 이유를 서면으로 첨부한다.** 여기서의 FP 는 안전 근거와 실행 반증이 받치는 FP 다.
쓰는 손은 Claude 라 그 한계를 따로 적는다 (「재지 못하는 것」 6).

### 3. 재현 가능한 공정성

2026년에 `temperature` 는 더 이상 통제변수가 아니다 —
Anthropic 은 Claude 4.7 이후 모델에서 이를 **제거했고 400 을 반환한다.**

> **"temperature 0 으로 고정했다"고 주장하는 2026년 벤치마크는
> 자기가 말한 실험을 하지 않은 것이다.**

게다가 **Anthropic 에는 `seed` 파라미터가 없다.** temperature 도 seed 도 없으니
Claude 실행은 **환원 불가능하게 확률적**이다.
→ 그래서 이 프로젝트는 **"재현 가능한 출력"이 아니라 "재현 가능한 프로토콜"** 을 주장한다.
횟수를 수집 전에 선언한 반복(기본 8) + 오차막대, 모든 원본 응답 아카이브, 그리고 실행마다
`RunManifest`(모델 ID · 프롬프트 해시 · 코퍼스 해시 · 도구 버전 · 하네스 SHA).

#### 그리고 공정성 함정 두 개를 정면으로 다룬다

**캐싱 비대칭** — Anthropic 캐싱은 **옵트인**이고 OpenAI 는 **기본 활성화에 해제 수단이 없다.**
그래서 "프롬프트당 N회 반복해서 중앙값"은 구조적으로 편향된다 —
2회차부터 OpenAI 만 공짜 캐시에 적중해서, 추론이 아니라 **prefill 생략을 측정**하고
**OpenAI 비용을 최대 90% 과소 보고**하게 된다.
→ 프롬프트 **맨 앞**에 nonce(캐싱은 prefix 매칭이라 뒤에 붙이면 무효) + 호출별 캐시 토큰 수 공개.

**effort 기본값 비대칭** — 모델마다 기본 effort 가 다르다
(설계 시점 조사: `claude-opus-5-5` `medium` / `claude-sonnet-5` `high`).
"기본값으로 비교했다"는 곧 한쪽에 더 많은 추론 예산을 준 것이다.
⚠️ 벤더 기본값은 바뀐다 — 그래서 **표를 믿는 대신 호출마다 명시**하고,
매니페스트에 실제 보낸 값을 남긴다.
→ 모든 호출에 effort 를 명시하고, 단일 점이 아니라 **비용/정확도 프런티어**로 보고한다.

## 지금 나오는 결과

`Ruff` 와 `mypy` 는 **이미 리뷰어다.** 지적을 내므로 채점할 수 있고,
채점 기준을 바꾸면 숫자가 바뀐다. 그래서 논지는 **모델 API 없이도 성립한다.**

### 결과 1 — 안전한 코드와 터지는 코드를 구별하지 못한다

`D002` 쌍은 `shell=True` 를 쓴다. decoy 는 커맨드가 모듈 상수라 안전하고,
twin 은 인자를 보간해서 진짜 취약하다.

| 파일 | 실제 | Ruff |
|---|---|---|
| `decoy.py` | **안전** (커맨드가 모듈 상수) | `S602 shell=True, security issue` |
| `twin.py` | **취약** (인자를 보간) | `S602 shell=True, security issue` |

**같은 룰, 같은 줄, 같은 판정.** PrimeVul 용어로 **P-V(과잉지적)** 이고,
왼쪽은 널리 쓰이는 프로덕션 분석기의 **확인된 False Positive** 다.

`D001` 은 반대다 — decoy 도 twin 도 아무것도 못 찾는다. twin 의 진짜 KeyError 를
놓친다. **확인된 False Negative.**

### 결과 2 — 같은 지적을 여러 정의로 채점하면 FP 가 **수십 배** 갈린다 [실측 · 150쌍]

이 프로젝트의 헤드라인이다. **지적은 하나도 바뀌지 않았다.** 정답 정의만 바꿨다.
리뷰어는 `ruff --select ALL` 이다 — 🔴 **편차는 룰 선택에 따라 달라지므로
어느 설정에서 잰 것인지 같이 적는다**(결과 6).

```
채점자                     TP   FP  판정불가  FP가능
provable_safety           0   17     756      o     <- 결함 주장만, 그것도 근거 범위 안만
injected_defect           0  773       0      o     <- Qodo 정의: 판정 불가 칸이 없다
paired_fix                0   18     755      o
static_corroboration      5    0     768      x     <- 구조적으로 FP 를 못 낸다
```

편차의 정체는 둘이다 — **① 한쪽이 「판정할 수 없다」고 둔 것을 다른 쪽이
「틀렸다」로 센다**(Qodo 계열에는 그 칸이 없다). **② 관례 주장(docstring 누락
같은 것)을 거짓 경보로 세느냐.** ②가 특히 크다 — 그 지적들은 **사실이기**
때문에 오탐으로 세면 맞는 지적을 오답으로 채점하는 것이 된다.

> 📊 **현재 수치는 [docs/MEASUREMENTS.md](docs/MEASUREMENTS.md) 에 있다.**
> 코퍼스가 자라면 `uv run codeproof report` 가 다시 만든다 —
> 산문에 숫자를 베껴 두면 반드시 낡기 때문이다.

> ⚠️ `static_corroboration` 의 FP 0 은 편차가 아니라 **범주 차이**다 —
> 합의 기반 정의는 구조적으로 FP 를 낼 수 없다(동의 부재 ≠ 반증).
> 그 0 을 편차에 넣으면 「0 → 44」로 부풀릴 수 있지만, 그건 우리가 비판하는 과장이다.
> 도구가 어휘를 확인하고 **자동으로 제외**한다.

### 결과 3 — 짝 판정도 채점자의 함수다

증명된 음성과 가드만 제거한 twin 을 짝으로 놓고 Ruff 를 `--select ALL` 로 돌린
PrimeVul 짝 채점이다. **리뷰어도 지적도 바꾸지 않고 정답 정의만 바꿨다** [실측 · 60쌍].

| 채점 정의 | 구별 성공 | P-V 과잉지적 | P-B 미탐지 | P-R 역전 |
|---|---:|---:|---:|---:|
| `provable_safety` | 0 | 3 | **54** | 3 |
| `injected_defect` (Qodo 계열) | 0 | 14 | 0 | **46** |

🔴 **같은 실행이다.** 한 쌍도 갈라내지 못했다는 데는 둘이 같지만, 한쪽은
「거의 다 놓쳤다」(P-B 54)고 말하고 다른 쪽은 「46쌍은 거꾸로 찾았다」(P-R 46)고 말한다 [실측 · 60쌍] —
리뷰어가 **어떻게** 실패했는지가 정의의 선택으로 정해진다.

⚠ **이 차이도 `ALL` 에서만 보인다.** `--ruff-select S` 로 좁히면 두 정의의 짝 판정이
**완전히 같아져**(0 · 3 · 56 · 1) 이견이 사라진다 [실측 · 60쌍]. 보안 룰만 쓰는 벤치마크였다면
「정답 정의는 결과에 영향이 없다」고 결론 내렸을 것이다 — 그리고 그건 틀렸다.

차이의 정체는 음성 쪽 지적을 무엇으로 세느냐다. `injected_defect` 에는
판정 불가 칸이 없어 **docstring 누락 같은 관례 지적까지 오탐으로** 센다.
그러면 거의 모든 음성이 「지적됨」이 되어 P-R(역전)로 떨어진다.

> 🔴 **철회한 숫자.** 이 표는 한때 `provable_safety` 의 구별 성공을 **11** 로 실었고,
> 「한쪽은 11건을 갈라냈다」가 이 절의 요지였다. **틀렸다.** 11건은 전부 twin 위의
> docstring · 스타일 지적(`D101` · `D103` · `RET504` …)이 결함 구간에 겹친 것이었다 —
> 관례 주장을 음성 쪽에서는 판정 불가로 돌리면서 twin 쪽에서는 탐지로 세고 있었다.
> 바로 아래 문단의 실수를 반대쪽에서 다시 한 것이다. 양쪽에 같은 경계를 두자 11 → 0 [실측 · 60쌍].

> 이 함정에 **내가 먼저 빠졌다.** 채점자가 위치 겹침만 보고 관례 주장을
> 오탐으로 세던 시절, FP 66건 중 45건이 `D103`(docstring 누락)이었다 —
> decoy 함수에 정말 docstring 이 없으니 **그 지적은 옳다.**
> 고친 뒤 FP 66 → 6 이 됐고, 그 과정에서 발표했던 결론 두 개를 철회했다.

**지적 단위로만 보면 이 사실이 전혀 보이지 않는다.** twin 쪽만 세면
Precision 이 높게 나오는데, 그 TP 는 안전한 쪽에도 똑같이 낸 지적이
우연히 결함 자리에 걸린 것이다.

### 결과 4 — 검증 레이어도 **대부분 구별하지 못한다**

파이프라인 3·4단계(인용 검증 · 가드 탐지 · 교차 확인 · 도달성)를 붙이고 측정했다.

```
D010-idempotent-retry        conf=0.55  guard=refutes       ← 안전 (가드 발견)
D010-idempotent-retry#twin   conf=0.85  guard=inconclusive  ← 취약

D002-shell-true-constant     conf=0.85  guard=inconclusive  ← 안전
D002-shell-true-constant#twin conf=0.85 guard=inconclusive  ← 취약  ⚠ 동일
```

`D010` 은 구별했다 — `_deliver` 안의 멱등 검사를 **callee-guard** 가 찾아냈다.
`D002` 는 구별하지 못했다 — "커맨드가 모듈 상수라 외부 입력이 닿지 않는다" 는
제어흐름이 아니라 **오염 추적(taint analysis)** 이 필요하고, 이 검증자는 그걸 못 본다.

> **못 보는 것을 문서에 적지 않으면 `SUPPORTS` 가 과신으로 읽힌다.**
> 그래서 각 검증자의 한계를 독스트링에 명시하고, 테스트가 그 문장의 존재를 강제한다.

### 결과 5 — 판정이 **매칭 손잡이에 흔들린다**

같은 결함을 두 도구가 다른 줄로 보고한다 — Ruff 는 호출 시작(L9),
bandit 은 `shell=True` 인자(L11)를 대표 줄로 둔다. 대표 줄로만 맞추면 결함 구간이 5–10 일 때
한쪽만 TP 가 된다 (bandit 은 호출 전체 L9–14 를 범위로도 주므로, 이 저장소는 보고 범위로 맞춘다).

```
[매칭 민감도] slack 을 바꾸면 판정이 흔들리는가   [실측 · 60쌍 · ruff ALL · provable_safety]
   slack  P-C  P-V  P-B  P-R
       0    0    3   54    3
       2    1    3   53    3
       5    1    3   53    3
      10    1    5   53    1
  🔴 불안정 (0→2, 5→10 에서 판정이 바뀐다)
```

Ruff 에서는 흔들림이 작다 — 거의 모든 짝에서 둘 다 침묵하기 때문이다. 결론이 실제로 갈리는 곳은
에이전트 비교다: 같은 짝 위의 claude − codex 차이는 slack 0 에서만 구별되고 2 부터 구간이 0 을
품는다 [실측 · 60쌍 · 생성물 「차이의 매칭 민감도」]. 어느 값을 고르느냐가 곧 결론이고, 그 값은
벤치마크마다 다르며 대개 **공개되지 않는다.**

> 🔴 **철회한 숫자.** 이 블록은 한때 「허용 오차 하나로 구별 성공이 11 에서 52 로 간다」를 실었다.
> 대부분이 slack 을 넓힐수록 결함 구간에 더 많이 걸린 twin 위의 관례 지적이었다 (결과 3 의 철회와
> 같은 원인) — 고치자 0 → 1 이다 [실측 · 60쌍].

**리뷰 품질 차이가 아니라 보고 관례 차이다.** 그래서 도구는 단일 값으로 결론을 내지 않고
**스윕해서 흔들리는지를 같이 보고**한다. 흔들리면 그 결론은 매칭 정책의 산물이다.

### 결과 6 — 룰 선택이 FP 도, **정의 간 편차도** 움직인다

같은 코드, 같은 채점자, 같은 코퍼스. `--ruff-select` 만 바꿨다 [실측 · 60쌍].

| 룰 선택 | 지적 | `provable_safety` FP | `injected_defect` FP | 두 정의의 편차 |
|---|---:|---:|---:|:---:|
| `F,E` | 0 | — | — | 잴 수 없다 |
| `S` | 4 | 4 | 4 | **1.0배** |
| `ALL` | 238 | **7** | **238** | **34배** |

**이게 이 프로젝트의 논지를 한 줄 명령으로 보여준다.** 보고되는 FP 율은
도구의 성질만큼이나 **측정자가 고른 설정**의 함수다.

🔴 **마지막 열이 더 중요하다.** 헤드라인인 「정의만 바꿔도 34배」[실측 · 60쌍]는
그 자체가 `ALL` 에서만 성립한다. 보안 룰만 고르면 두 정의가 **정확히 일치한다** —
편차의 정체가 「판정 불가로 둘 것을 오답으로 세느냐」인데, 보안 룰은 전부
근거 범위 안의 결함 주장이라 이견이 생길 자리가 없기 때문이다.

> 이건 F5 의 반복이다. 거기서 배운 것은 「구별 성공률은 리뷰어가 아니라
> **(리뷰어 × 채점자)** 의 성질」이었다. 같은 규율을 룰 선택 축에는 적용하지
> 않고 있었다 — 편차 역시 **(채점자 × 룰 선택)** 의 성질이다.
> 그래서 이 저장소의 모든 편차 주장은 이제 룰 선택을 같이 적는다.

`ALL` 의 판정불가 231건이 핵심이다 — 저건 안전 근거가 덮지 않는 범위의 지적이라
**참인지 거짓인지 말할 수 없다.** 순진한 벤치마크라면 전부 FP 로 세서
끔찍한 FP 율을 보고했을 것이다.

> ⚠️ 직접 쓴 decoy 다. **측정이 아니라 예시다.** 숫자로 발표하려면 150건이
> 필요하고, 도구가 실행마다 그렇게 경고한다.

> 있고 테스트도 돌지만(결과 4 가 그 측정이다), 「PR 하나를 리뷰하는 명령」은
> **일부러 만들지 않았다.** 이 저장소의 논지는 오프라인 측정 경로이고,
> 안 되는 것을 `--help` 에 올려 두면 쓰는 사람이 속는다.
> `--help` 의 7개 명령은 전부 실제로 동작하며, 테스트가 그것을 강제한다.

## 측정 설계

### 양성은 만들지 않는다

> 자기 숙제를 자기가 채점하지 않는다.

결함 탐지는 **기성 벤치마크를 그대로 쓴다**:
[c-CRAB](https://arxiv.org/abs/2603.23448) (410건, 339건 테스트 검증, CC BY 4.0) ·
[AACR-Bench](https://github.com/alibaba/aacr-bench) (시니어 80명+ 3라운드, Apache-2.0).

라벨링 시간 0, 자기편향 시비 원천 차단.

### 음성 4개 층 — 여기에 전 예산을 쓴다

| 층 | 내용 | 무엇을 재는가 |
|---|---|---|
| **A** | 변이 주입 | recall **바닥선** — "기계적 경계 뒤집기도 못 잡으면…" |
| **B** | 짝지은 수정후 버전 | **과잉지적** — 같은 함수, 가드만 다름 (**공짜**) |
| **C** | 매칭 Clean PR | 기존 문헌과의 비교 가능성 *(v2)* |
| **D** | **직접 쓴 near-miss decoy** | **증명 가능한 FP** ← 차별점 |

**B층이 공짜인 이유**: 모든 양성의 *수정된 버전*이 완벽히 매칭된 음성이다.
[PrimeVul](https://arxiv.org/abs/2403.18624) 의 짝 채점(P-C / **P-V** / P-B / P-R)을 쓰면
**P-V = 과잉지적률**이 바로 나온다. PrimeVul 에서 7B SOTA 가
BigVul F1 68.26% → **3.09%** 로 무너진 게 이 채점 때문이다.
**과잉지적은 짝을 지어야만 보인다.**

**D층 예시** — 전부 "버그처럼 보이지만 안전":
- 호출부가 non-null 을 보장하는 null 역참조
- 호출부가 이미 쥐고 있는 락 위의 경쟁 상태
- 계약상 반열린 구간이라 **맞는** off-by-one
- 보간값이 `Enum` 멤버라 안전한 SQL 조립
- `unsafe_` 접두사지만 실제로는 검증된 변수
- 진짜 `sanitize()` 옆의 no-op shim

작성 규칙: ① 리뷰어가 **진짜 작업으로 인식할** 변경 ② **안전 근거를 서면 첨부**
③ **가드만 다른 진짜 버그 쌍둥이**와 페어 ④ **근거를 반증하는 공격을 코드로 첨부**.

#### 🔴 "증명된 음성" 이라는 라벨을 어떻게 믿을 것인가

이게 이 코퍼스의 급소다. 라벨이 틀리면 **맞는 지적을 FP 로 채점**하게 되고,
그러면 이 프로젝트가 다른 벤치마크를 비판하는 바로 그 오류를 저지르는 셈이다.

**한 번 당했다.** `D015` 를 처음 쓸 때 `Semaphore(4)` 를 가드로 삼았는데 —
세마포어는 4 스레드 동시 진입을 허용하므로 그 경쟁은 **실제로 일어난다.**
안전 주장이 거짓이었고 **검증 규칙 11개를 전부 통과했다.** 손으로 검토하다 잡았다.

형식 검증은 근거가 *참인지* 볼 수 없다. 그래서 **근거를 실행 가능하게** 만들었다 —
쌍마다 `proof.py` 가 결함을 **실현하려 시도**한다:

```python
def attack(mod: ModuleType) -> bool:   # 결함이 실현되면 True
```

| 조건 | 무엇을 보장하는가 |
|---|---|
| `attack(decoy) is False` | 안전 근거가 참이다 |
| **`attack(twin) is True`** | **공격이 실제로 결함을 잡을 수 있다** |

**두 번째 줄이 핵심이다.** 이게 없으면 `return False` 만 적어도 통과한다 —
공격의 능력을 twin 으로 증명한다. Juliet 의 goodG2B/goodB2G 구조를 코드가 아니라
**증명 자체**에 적용한 것.

검산: `D015` 의 세마포어 버전을 복원하면 `attack(decoy)` 가 True 가 되어 걸린다.
**11개 형식 규칙이 놓친 것을 잡는다.** 이 회귀를 테스트로 고정해 뒀다.

#### 면제 목록을 없앴다

전에는 실행 검증을 중앙 파일에 손으로 적고, 못 쓰겠는 건 `UNTESTED_BY_DESIGN` 에
사유와 함께 올렸다. 다시 세어 보니 그 시점의 19쌍 중 **8건(42%)에 twin 반증이 없었고,
그중 하나가 `D015`** 였다 — 우연이 아니라 인과다. 그리고 면제 사유 **다섯 개가
전부 틀렸다**(동시성·자원수명·경로탈출 전부 검증 가능했다).

「너무 어렵다」가 조용히 「검증 안 됨」이 되는 자리였다. 면제 기구를 제거했다 —
**공격을 못 쓰면 그 decoy 는 싣지 않는다.** 현재 코퍼스 전부 통과 상태다
(쌍 수는 [docs/MEASUREMENTS.md](docs/MEASUREMENTS.md) 참조).

> 그래도 **증명이 아니라 반증 시도**다. 공격이 약하면 통과한다.
> 경쟁은 줄 단위 추적(`race_window`)으로 창을 벌리지만 확률적이다 —
> 그것 없이는 16스레드 × 5000회에 갱신 손실이 **0건**이었다.

`corpus/decoys/` 를 편집하면 **훅이 자동으로 규격을 검사**하고, 위반이면 그 이유를 Claude 에게
돌려줘 고치게 한다 — 편집 자체를 되돌리지는 않는다
(`.claude/hooks/decoy-validate-guard.sh`). 훅은 형식 13규칙(`proof.py` 존재 포함)만
보고, 근거가 참인지는 테스트가 돌려서 본다.

미끼가 실제로 물리는지도 잰다:

```bash
uv run codeproof decoy stats
#   시험됨: 6/60 (10%)
#   type_narrowed  0/5  .....   <- 구조적. Ruff 에 룰이 없고 mypy 는 좁힘을 인정한다
```

🔴 **10% 는 코퍼스 결함이 아니다.** `ruff(ALL)` 5건 · `mypy` 0건 · `pylint` 2건인데
**pylint 2건은 Ruff 가 이미 잡는 것**이다. 세 도구가 무는 지점이 같다 —
위험 API 와 타입 오류뿐. 락 보유 · 방어적 복사 · 반열린 계약 같은 논리형 덫은
**어느 린터도 못 본다.** 그게 D층이 존재하는 이유다.

**「안 물림 = 나쁨」이 아니다** — 추론이 필요한 미끼일 수 있고, 그건 LLM 리뷰어가
있어야 안다. 정적분석기만으로는 「미시험」과 「미끼가 약함」을 구별할 수 없고,
도구가 구별했다고 말하지 않는다.

자동 생성 음성은 측정력이 없다 — [SQuAD 2.0](https://arxiv.org/abs/1806.03822) 이
손으로 쓴 적대적 음성으로 최고성능을 85.8 → **66.3 F1** 로 떨어뜨려 증명했다.
이 코퍼스는 템플릿으로 찍지 않고 쌍마다 근거와 실행 반증을 붙이지만, 쓰는 손이 사람이 아니라
Claude 다 — SQuAD 2.0 과 같은 조건은 아니다 (「재지 못하는 것」 6).

### 규모 — 타협하지 않는 부분

Wilson 95% 신뢰구간 반폭:

| 음성 n | p=0.10 | p=0.30 |
|---:|---:|---:|
| 50 | ±8.5pp | ±12.3pp |
| 100 | ±6.0pp | ±8.8pp |
| **150** | **±4.8pp** | **±7.3pp** |

**음성 100개 미만이면 FPR 은 숫자가 아니라 느낌이다.** 목표는 150개.

#### 🔴 더 중요한 이유 — 집계가 아니라 **분류별 이질성**

집계 FPR 의 CI 를 좁히는 것만이 이유가 아니다. 더 큰 이유가 측정하다 드러났다.

D층 집계 FPR 은 「이 도구의 오탐률」이 아니라 **「내가 고른 미끼 분류 구성비에서의
오탐률」**이다. 분류마다 물리는 정도가 다르기 때문이다 — [실측 · 60쌍]:

```
idempotent_retry      14.3%  [ 4.0%, 39.9%]     <- 가장 잘 문다
constant_only_sink    13.6%  [ 4.7%, 33.3%]
...
type_narrowed          0.0%  [ 0.0%, 14.9%]     <- 전혀 안 문다 (11종이 0.0%)

현재 구성비 :  2.9%   ·   균등 구성비 : 2.7%
🔴 구성비만 바꿔 도달 가능 : 0.0% ~ 14.3%
```

**코드도 도구도 채점자도 바꾸지 않고 구성비만 바꿔** 0% 도 14.3% 도 보고할 수 있다.
(전체 표는 [MEASUREMENTS](docs/MEASUREMENTS.md) 에 있다.)
채점 기준 편차와 같은 종류의 손잡이인데, 자기 코퍼스의 구성비를 손잡이로 선언한
벤치마크를 보지 못했다.

#### 두 번째 축 — **가드를 찾으려면 어디를 봐야 하는가**

미끼 분류만으로는 코퍼스가 쏠렸는지 알 수 없다. 가드가 늘 호출부에 있으면
리뷰어가 「위험한 줄이 비공개 헬퍼면 호출부를 보라」는 **요령만 익혀도** 점수가
나온다 — 추론이 아니라 구조를 학습하는 것이고, 짝 채점이 per-finding 에 대해
지적하는 그 문제가 한 층 위에서 반복된다.

그래서 직교하는 두 번째 축을 **자동 도출**한다 (`meta.toml` 에 필드를 더하지
않는다 — 손으로 적게 하면 틀리고, 틀려도 아무도 모른다):

| 가드 위치 | 리뷰어가 해야 하는 일 |
|---|---|
| `local` | 같은 함수 안 — 지역 추론으로 끝 |
| `caller` | 부르는 쪽을 거슬러 올라간다 |
| `callee` | 이름이 비슷한 이웃을 구별한다 |
| `module` | 함수 밖(상수·타입·클래스 불변식)을 본다 |

> 🔴 **철회한 주장.** 여기 한때 「가드가 멀수록 더 문다」(`local` 18.2% →
> `module` 45.2%)를 실측으로 적었다. **그 숫자는 틀렸다.** 채점자가 `D103`
> (docstring 누락) 같은 **관례 주장**까지 오탐으로 세고 있었고, 함수가 많은
> decoy 가 그런 지적을 더 받았을 뿐이다. 고친 뒤 순서가 **반대로** 뒤집혔다
> (`caller` 0.0% → `local`, 49쌍 시점). 아래 「관례 주장」 절을 보라.
> 현재 수치는 [MEASUREMENTS](docs/MEASUREMENTS.md) 에 있다.

#### 🔴 관례 주장은 거짓 경보가 아니다 — 이 프로젝트가 저지를 뻔한 오류

`ProvableSafetyGrader` 는 「안전 근거가 덮는 **줄 범위** 안의 지적은 FP」로
채점했다. 위치 겹침을 「주장이 덮는다」로 읽은 것이다. 그런데 안전 근거는
**특정 결함**에 대한 것이지 그 줄에 대한 것이 아니다.

[실측 · 49쌍] `--select ALL` 에서 FP 66건 중 **45건이 `D103`**
(docstring 누락)이었다. decoy 함수에 정말 docstring 이 없으니 **그 지적은 옳다.**
맞는 지적을 오답으로 채점한 것이고, 그건 우리가 기존 문헌에 대해 비판하는
바로 그 오류(§8 판정 불가)와 같은 종류다.

**고친 방법.** Ruff 는 룰마다 `category` 를 직접 준다(`ruff rule --all`,
16ms). `pedantic`·`style`·`formatting`·`restriction` 은 관례 주장이므로
안전 근거가 반박할 수 없다 → `UNDECIDABLE`. 접두사로 짐작하지 않는 이유는
`TRY003`·`PERF203` 이 접두사로는 다른 계열인데 Ruff 는 둘 다 `pedantic` 으로
분류하기 때문이다.

**결과 — 결론 두 개가 뒤집혔다:**

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| `provable_safety` FP | 66 | **6** |
| 미끼 시험률 | 84% | **10%** |
| 가드 위치 순서 | `local` 최소 → `module` 최대 | **반대** |

노이즈가 신호처럼 보였다. 정적분석기는 이 코퍼스를 **거의 시험하지 못한다** —
그게 진짜 결과다.

#### 🔴 그리고 여기서 optional stopping 을 막았다

37쌍 시점에 **CI 가 갈렸다** — `type_narrowed ≤20.4% < 29.1%≤ constant_only_sink`.
(25쌍 시점에는 3.2pp 겹쳐 있었다.)

여기서 멈추고 「분류마다 다르다」를 발표하고 싶어진다. **그게 정확히
optional stopping 이다** — 어떤 잡음이든 충분히 들여다보면 원하는 모양이
한 번은 나오고, 그때 멈추면 그 모양이 결론이 된다.

그래서 **분류당 목표 쌍 수(10쌍 × 14종 = 140)를 미리 박아 두었고**, 도구가
미달 상태의 판정에 자동으로 꼬리표를 붙인다.

그런데 위의 「갈렸다」는 판정 방식도 틀려 있었다 — 극단 두 분류의 **지적 단위** 구간이라,
차이가 없어도 「실재한다」가 최대 37.6% 나온다 [실측 · 모의실험]. 지금은 **decoy 단위 순열 검정**으로
분류 전체를 한 번에 본다 (거짓 양성 3.4~4.4%). 바꾼 시점이 60쌍 결과를 본 뒤라는 것과 그 이유는
[DESIGN §3.5](docs/DESIGN.md) 가 적는다.

```
⚖ 분류 간 차이가 **실재한다** - p=0.0058 (decoy 단위 순열 검정 · 14종 · decoy 60개 · 순열 9999회).
  ⚠ 다만 14종이 아직 분류당 목표 10쌍에 못 미친다 - 선언한 표본을 다 채운 뒤의 판정이라야 결론이다
```

→ 150 목표는 집계 FPR 정밀도와 분류당 최소 10쌍을 함께 채우는 값이다. 이질성 검정의 검정력은
  목표 150쌍에서도 69% 라 [실측 · 모의실험], 기각하지 못하면 「같다」가 아니라 「모른다」다.

[실측 · 150쌍] 14종이 모두 선언한 분류당 10쌍 이상을 채운 뒤의 판정은 「실재한다」(p=0.0001 · `ruff --select ALL`)다 —
이제 꼬리표 없는 결론이다. 같은 표본에서 가드 위치 축은 p=0.32 로 「모른다」에 머문다 (생성물의 「미끼 분류」 · 「가드 위치」).

## 지표

| 규칙 | 이유 |
|---|---|
| **층을 섞지 않는다** | 유리한 층 뒤에 숨을 수 있다 |
| **FPR 두 정의 병기** | 샘플당 지적 수 / 지적 받은 샘플 비율 |
| **Youden's J = TPR+TNR−1** | 유병률 독립 헤드라인 (OWASP 선례) |
| **모든 수치에 Wilson 95% CI** | 점추정만 내는 건 측정이 아니다 |
| **매칭 함수 신뢰도 보고** | 매칭 함수 자체가 라벨 원천이다 |
| **FPR 10% 앵커** | [Tricorder](https://research.google.com/pubs/archive/43322.pdf) 의 개발자 이탈 임계 |

### 정확도와 지연을 같은 실험에서 재지 않는다

Batch API 는 50% 싸지만 **지연 비교를 무효화한다** — 양쪽 결과 스키마에
**요청별 타이밍 필드가 아예 없고**, Anthropic 은 batch 에서 `stream: true` 를 거부해
TTFT 가 구조적으로 정의되지 않으며, 결과가 **임의 순서**로 돌아와 도착 순서 복원조차 안 된다.

→ 정확도·비용은 batch 로, **지연은 별도의 동기·스트리밍 소규모 실험**으로.
  둘을 하나의 "성능" 점수로 병합하지 않는다.

그리고 양 벤더 모두 **구조화 출력 스키마를 첫 호출에 컴파일해 24시간 캐시**한다 —
워밍업 없이 재면 첫 시행이 스키마 컴파일 시간이다.

### 두 모델은 독립이다 — 비교하되 투표하지 않는다

| 오염 경로 | 차단 |
|---|---|
| 한 모델이 다른 모델 지적을 채점 | v1 채점자는 전부 **비-LLM** |
| 한 모델 프롬프트에 다른 모델 지적이 들어감 | `review(target, ...)` 에 **넣을 자리가 없다** |
| 교차모델 합의를 confidence 로 사용 | triage 로 강등 (ρ 0.20–0.59) |
| 서로 다른 모델 지적을 한 관측으로 묶음 | `MixedReviewerError` 로 **거부** |

마지막 항목이 미묘하다 — Claude 와 Codex 지적을 한 집합에 넣으면
둘 다 찾은 것이 `2/2` 로 보여서 **출현 빈도가 자기일관성이 아니라
교차모델 합의를 재게 된다.** 조용한 투표다. 타입이 막는다.

### LLM 판정자를 쓰지 않는다

채점에 LLM 판정자를 쓰면 **Claude vs Codex 비교가 무효화된다.**

- **자기선호 편향** — 판정자는 저-perplexity 텍스트를 선호하고,
  자기 출력은 구조적으로 자기에게 저-perplexity다. 기전이 규명돼 있고 모델 크기에 따라 강해진다.
- **코드 도메인의 판정자 일치도가 전 도메인 최악** — pairwise κ **0.159**, Fleiss κ **0.070**.
- **일관성 ≠ 타당성** — test-retest 0.99 와 위치편향 0.19 가 공존한다.

→ 채점자는 **비-LLM 증거 기반**으로 설계한다.

## ⚠️ 이 프로젝트가 재지 *못하는* 것

포트폴리오용이라고 해서 과대포장하지 않기 위해, 한계를 먼저 적는다.

**1. 결함 탐지는 리뷰의 1/8 이다.**
실제 리뷰 코멘트 중 결함 지적은 **14% 뿐**이다
([Bacchelli & Bird](https://sback.it/publications/icse2013.pdf), 570건 카드분류).
최대 범주는 *코드 개선* 29%. 결함 탐지만 채점하는 벤치마크는
**리뷰어가 하는 일의 8분의 1** 을 재고 있다.

**2. 일치와 유용은 다르다.**
c-CRAB 에서 정답 테스트를 통과한 건 20–32% 인데,
사람이 유용하다고 평가한 건 **84%** 였다.
이 둘을 섞는 게 이 분야 숫자가 과대포장되는 가장 흔한 경로다.

**3. 50:50 세트의 precision 은 프로덕션 precision 이 아니다.**
그래서 `(TPR, FPR)` 로 보고한다 — 누구나 자기 유병률에서 재유도할 수 있게.

**4. 오염 내성은 층마다 다르다.**
A·D 층은 면역(직접 생성/작성), **B·C 층은 아니다.**

**5. A층(변이 주입)은 현실적이지 않다.**
Google 실측으로 변이체의 **85%를 개발자가 무익하다고 분류**했고,
실제 결함은 3–4 토큰을 바꾸는데 변이체는 1 토큰이며,
실제 결함의 **17%는 어떤 변이체와도 짝지어지지 않는다.**
→ **recall 바닥선으로만** 쓰고 현실성을 주장하지 않는다.

**6. D층 정답은 측정 대상 한쪽과 같은 패밀리가 썼다.**
decoy 는 Claude 가 쓰고(모든 커밋에 공동 작성자로 남아 있다) 독립 검토도 Claude 가 한다.
생성기가 만든 벤치마크에서는 그 생성기의 점수가 부풀고, 부푼 몫의 67–80% 가 **틀린 정답 라벨**이었다
([Silencer](https://arxiv.org/abs/2505.20738) — 수학 · 언어 이해, 코드는 다루지 않았다).
같은 패밀리의 맹점에 틀린 라벨이 남으면 Claude 리뷰어에게는 정답, Codex 에게는 FP 로 채점되어
claude − codex 차이가 Claude 쪽으로 기운다. 실행 반증(`proof.py`)이 라벨을 실행으로 묶어 그 통로를
좁히지만 닫지는 못한다 — 반증은 쓴 쪽이 떠올린 공격만 친다. [실측 · 14쌍 파일럿] Claude 검토를 거친 쌍을
Codex 가 한 번씩 보게 했더니 위협 모델 안의 라벨 문제가 **3/14** [95% 구간 7.6%, 47.6%] 쌍에서 재현됐다
(거짓 주장 0 · 넓은 주장 2 · 덮는 범위 안의 주장 밖 결함 1). [실측 · 나머지 102쌍] 같은 방식으로 나머지 쌍을 보게
했더니 **31/102** [22.3%, 39.9%] 쌍에서 재현됐다 — 같은 검토를 거치지 않은 초기 쌍 D001~D060 이 24/60, 검토를 거친
D061~D116 의 파일럿 밖 쌍이 7/42. 5라운드부터는 같은 감사를 라운드마다 세 번째 검토 렌즈로 두고 [실측 · 5라운드 14쌍]
1/14 쌍, [실측 · 6라운드 20쌍] 3/20 쌍에서 재현됐다. 주장만 고치면 되는 쌍과 에이전트 묶음 밖 쌍은 고쳤고,
[실측] 에이전트가 잰 D001~D060 에서 코드를 고쳐야 하는 16쌍은 검증한 수정안만 실었다 — 적용하면 그 묶음을 다시 재야 해서다.
그때까지 에이전트 숫자는 이 라벨 문제를 안고 있다 (DESIGN §9 의 5).

## 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 런타임 | Python **≥3.14** | — |
| 패키지 | **uv** | — |
| 정적분석 | **Ruff** (JSON) + **mypy** (JSON Lines) | 둘 다 subprocess · **호스트 설정과 캐시를 격리** |
| AST | stdlib `ast` | 의존성 0 |
| 도달성 | `ruff analyze graph` (모듈 단위) | 전용 호출그래프 도구가 **전멸**했다 (아래) |
| diff | **unidiff** | GitPython 은 hunk 파싱 자체가 없다 |
| LLM | `anthropic` · `openai` **직접** | 아래 |
| 저장 | SQLite (외래키로 E1 강제) | 재현성 |
| 출력 | SARIF 2.1.0 | GitHub Code Scanning 호환 |
| 구조화 출력 | `output_config.format` / `strict:true` | 강제 tool use 는 최신 Claude 에서 **400** |

### LiteLLM 을 쓰지 않는 이유

래퍼 5종(LiteLLM · LangChain · instructor · PydanticAI · llm)이 전부
**OpenAI 모양의 `usage` 객체로 정규화**하는데, **프로바이더마다 "토큰"의 정의가 다르다** —
Anthropic 의 `input_tokens` 는 캐시 토큰을 **제외**하고, OpenAI 는 **포함**한다.
즉 정규화 레이어 자체가 손실 지점이고, 그게 바로 도입하게 되는 레이어다.

결정적으로, 관련 이슈들이 **미해결로 종료**됐다:

| 이슈 | 상태 |
|---|---|
| LiteLLM #23731 — 토큰 수 오류 | **not planned 로 종료** + 원본 응답 바디가 없어 재유도 불가 |
| PydanticAI #4364 — Anthropic `input_tokens` 재기준화 | 종료, 의도된 동작 |
| LangChain #32818 — 동일 | 종료, 의도된 동작 |

출력이 **토큰 수와 지연시간 그 자체**인 벤치마크에서는 실격 사유다.
→ `Protocol` 하나 위에 얇은 어댑터 2개, `max_retries=0`,
**모든 호출의 원본 응답을 그대로 영속화.**

### 측정 도구는 호스트 환경에서 격리한다

측정 도구가 실행되는 레포의 설정을 주워오면 **같은 코퍼스가 레포마다 다른 숫자**를 낸다.
실제로 두 번 물렸다:

- mypy 가 이 레포의 `pyproject.toml` `strict = true` 를 주워왔다.
  그러면서 `config_signature()` 는 `strict=False` 라고 **거짓을 기록**했다.
- mypy 증분 캐시가 **이미 삭제된 임시 디렉터리 경로**의 진단을 돌려줬다.

→ `--config-file=/dev/null` · `--no-incremental` · `--cache-dir=/dev/null` 로 격리.
  Ruff 는 `--isolated`. 두 도구 모두 코퍼스의 파이썬 판(3.14)을 명시한다 — 없으면 Ruff 는 3.10 으로 본다.

그리고 대상마다 subprocess 를 띄우지 않는다 — **한 번에 일괄 분석**한다.
[실측] 30 대상 기준 ruff **9.9배**, mypy **33배**. 테스트가 「일괄 == 개별」을 강제해서
속도 최적화가 숫자를 바꾸지 못하게 한다.

### 파이썬 호출그래프 도구는 전멸했다

PyCG(2023 아카이브) · JarvisCG(2026-03 아카이브) ·
**Pyre/Pysa(2026-06 Meta 아카이브)** · scalpel(2022 정지) · rope(문법 지원 3.10까지).

→ v1 은 모듈 단위 도달성만. 함수 단위(LibCST + jedi 직접 조합)는 확장점으로 연기.

```
src/codeproof_ai/
├── domain/      # 의존성 0 — 나머지 전부가 이걸 import 한다

├── verify/      # [3][4] 런타임 · 라벨 불필요
├── eval/        # [5][6] 오프라인 · 라벨 필수   ← verify 와 절대 안 섞는다
├── store/       # SQLite
├── api/         # FastAPI (v2)
└── cli.py       # 주 진입점

corpus/          # 🔴 별도 프로젝트 · 별도 lock
                 #    벤치마크 툴체인이 3.14 와 충돌한다
```

### 확장점 — 전부 Protocol

| Protocol | 확장 방법 |
|---|---|
| `Analyzer` | `analysis/<lang>/` 추가 → **Java 지원은 디렉터리 추가만으로** |
| `ReviewProvider` | `llm/<provider>.py` 추가 |
| `Verifier` | `verify/<rule>.py` 추가 |
| `Grader` | `eval/grading/<name>.py` 추가 |

### 레이어 규칙 — 단 하나

> **`domain` 은 아무것도 import 하지 않는다.**

어기면 도메인 테스트가 LLM 키를 요구하기 시작한다.

## 사용법

```bash
# ── 준비 상태 ───────────────────────────────────────────
codeproof doctor

# ── 측정 (자격증명 불필요) ──────────────────────────────
codeproof measure --analyzers ruff,mypy              # 기본 룰 선택
codeproof measure --analyzers ruff --ruff-select ALL # 손잡이를 바꿔 본다
codeproof history --limit 5                          # 저장된 실행
codeproof history --repro <config-hash>              # 같은 설정끼리 재현성

# ── 측정값 문서 생성 ────────────────────────────────────
codeproof report                  # docs/MEASUREMENTS.md
codeproof report --check          # 낡았으면 exit 1 (CI 용)

# ── 코퍼스 ──────────────────────────────────────────────
codeproof decoy validate --strict # 규격 13종
codeproof decoy stats             # 미끼가 실제로 물리는지
codeproof decoy new D0XX-짧은-설명
codeproof decoy mutants           # 쌍마다 실린 변이로 증명을 다시 깬다 (경쟁 변이는 30번)

# ── 외부 리뷰어 가져오기 (자격증명 불필요) ──────────────
codeproof import --from out --name semgrep --identity "1.2.3"
codeproof export --out agent-in                      # 에이전트 입력 (프롬프트 + 스키마 · --docstrings keep|neutral)
scripts/review-with-agent.sh claude agent-in claude-out --effort low
codeproof import --from claude-out --name claude-code --kind agent   # RUN.json 이 정본
codeproof pack --from claude-out --out results/agent/claude-code     # 생성물에 싣는 묶음 (두 파일)

# ── 모델 (자격증명 필요) ────────────────────────────────
codeproof eval --providers claude,codex --effort high --samples 8
```

🔴 **안전 근거가 참인지는 `decoy validate` 가 못 본다.** 그건 쌍마다 있는
`proof.py` 를 돌리는 테스트가 본다:

```bash
uv run pytest tests/corpus/test_proofs.py
```

증명이 twin 하나만 깨는지, 그럴듯한 약화 전부를 깨는지는 쌍의 `mutants.py` 가 본다 — 약화는 깨야 하고
주장이 정하지 않은 것만 바꾼 안전한 변형은 통과해야 한다 (`tests/corpus/test_mutants.py`).

### 처음 받았다면 — 한 줄로 재현 확인

```bash
./scripts/verify.sh   # 1분 남짓 · API 키 불필요 · 재현 안 되면 exit 1
```

헤드라인이 이 기계에서 재현되는지, 그게 **설정의 함수**인지, 가드가 공허하지
않은지를 순서대로 검사한다. 전체 절차와 해설은 [docs/VERIFY.md](docs/VERIFY.md).

같은 스크립트를 GitHub Actions 가 main push 와 PR 마다 Linux · macOS 새 환경에서 ruff · mypy · pytest 와 함께
돌린다([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) — 직접 돌리기 전에 [실행 기록](https://github.com/manners-parkpro/codeproof-ai/actions/workflows/ci.yml)부터 볼 수 있다.
초록불이 말하는 것은 「새 기계에서도 같은 검사가 통과한다」까지다. 검사가 충분한지는 VERIFY.md 가 다룬다.

### 가드가 공허하지 않은지 확인한다

```bash
./scripts/falsify.sh          # 불변식을 일부러 깨고 가드가 우는지 본다
./scripts/falsify.sh --list   # 시나리오 목록
```

테스트가 통과하는 것은 「가드가 있다」의 증거가 아니다. 깨뜨렸는데도 통과하면
그 가드는 없는 것과 같다 — 실제로 **공허한 가드 두 개를 그렇게 잡았다.**
전체 절차는 [docs/VERIFY.md](docs/VERIFY.md) 에 있다.
