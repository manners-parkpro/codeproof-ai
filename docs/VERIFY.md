# 검증 프로토콜 — 이 저장소의 주장을 직접 무너뜨리는 법

이 문서는 「잘 만들었다」를 설득하려고 쓰지 않았다. **무엇을 어떻게 반증하는지**를
적었다. 이 프로젝트의 논지가 「측정 선택이 숫자를 만든다」이므로, 그 논지는
**남이 손잡이를 돌려서 숫자가 움직이는 것을 볼 때만** 성립한다.

그래서 이 문서의 성공 기준은 특이하다 — **당신이 돌려서 내 숫자가 흔들리면
그게 내 주장이 맞았다는 뜻이다.**

> 읽는 사람: 이 저장소를 처음 받은 사람. 파이썬만 알면 된다.
> 전제: `uv` 설치 · 네트워크(첫 `uv sync`). API 키는 **필요 없다** — 모델 숫자(T6)까지.

---

## 0. 한 줄로 — `./scripts/verify.sh`

따라 칠 것이 하나면 이것이다. **1분 남짓, API 키 불필요** [실측 · 새 클론 · venv 생성 포함 69초].

```bash
./scripts/verify.sh
```

아래 T0~T4 와 생성물 대조(에이전트 층 재채점 포함 — T6)를 순서대로 돌리고
각 단계가 무엇을 증명하는지 말해 준다.
🔴 **재현되지 않으면 크게 실패하고 `exit 1` 이다** — 항상 초록불이 켜지는
스크립트는 아무것도 증명하지 못한다. 기대값을 숫자로 박지 않고 **관계**를
검사한다(`ALL` 에서는 두 정의가 다르고 `S` 에서는 같다). 코퍼스가 자라도
거짓말하지 않기 위해서다.

나머지 절은 그 스크립트가 각 단계에서 **무엇을 왜 보는지**의 해설이다.

## T1 — 헤드라인 재현 (30초)

```bash
uv run codeproof measure --analyzers ruff --ruff-select ALL --store none
```

`[채점 기준 편차]` 블록을 본다. 증명 가능하게 안전한 코드 위에서 나온 **같은
지적 집합**을 네 가지 정답 정의로 채점한 결과가 나란히 선다.

확인할 것은 **숫자가 아니라 구조**다:

- 모든 채점자가 **같은 지적**을 본다 (`findings` 가 하나뿐이다)
- 그런데 FP 칸이 채점자마다 다르다
- `static_corroboration` 은 **편차 계산에서 빠진다** — 합의 기반 정의는
  구조적으로 FP 를 못 내므로, 그 0 을 넣으면 범주 차이를 편차로 부풀리게 된다

> 🔴 **여기서 의심해야 할 것**: 「자기한테 유리한 채점자만 골라 넣은 것 아닌가?」
> 답은 T2 가 준다 — 내 헤드라인이 성립하지 **않는** 설정도 내가 적어 뒀다.

생성된 수치는 [MEASUREMENTS.md](MEASUREMENTS.md) 에 있고, 그 파일이 최신인지는
`uv run codeproof report --check` 가 판정한다(낡았으면 `exit=1`).

## T2 — 손잡이 실험 ⭐ (2분)

**이 프로젝트를 15분에 판단해야 한다면 여기만 보면 된다.**

같은 코드 · 같은 코퍼스 · 같은 채점자. `--ruff-select` 하나만 바꾼다.

```bash
for sel in ALL S F; do
  echo "=== --ruff-select $sel ==="
  uv run codeproof measure --analyzers ruff --ruff-select "$sel" --store none 2>&1 \
    | grep -A6 '채점 기준 편차'
done
```

나오는 것 [실측 · 60쌍]:

| `--ruff-select` | 지적 | `provable_safety` FP | `injected_defect` FP | 두 정의의 차이 |
|---|---:|---:|---:|:---:|
| `ALL` | 238 | 7 | 238 | **34배** |
| `S` | 4 | 4 | 4 | **없다 (일치)** |
| `F` | 0 | — | — | 잴 수 없다 |

🔴 **내 헤드라인이 성립하지 않는 설정이 있다.** 보안 룰만 고르면 두 정의가
정확히 일치한다. 편차의 정체가 「판정 불가로 둘 것을 오답으로 세느냐」인데,
보안 룰은 전부 안전 근거 범위 안의 결함 주장이라 이견이 생길 자리가 없다.

짝 채점도 같다 — `ALL` 에서 `provable_safety` 미탐지 54 · 역전 3, `injected_defect` 역전 46 으로
갈리던 짝 판정이 `S` 에서는 **똑같아진다** (0 · 3 · 56 · 1) [실측 · 60쌍]. (한때 여기 「구별 성공
11 · 0」을 적었다 — 11 은 twin 위의 관례 지적이었다. README 결과 3 의 철회를 보라.)

**그래서 이 결과의 올바른 읽기는 이것이다.** 「정답 정의가 결과를 바꾼다」가
아니라, **「정답 정의가 결과를 바꾸는지 여부 자체가 룰 선택에 달려 있다」**.
보안 룰만 쓰는 벤치마크였다면 「정의는 영향 없다」고 결론 내렸을 것이고,
그 결론은 자기 설정 안에서만 참이다.

> 이건 이 저장소가 자기 규율을 자기한테 적용해서 나온 것이다. `CLAUDE.md` 의
> F5 가 「구별 성공률은 리뷰어가 아니라 **(리뷰어 × 채점자)** 의 성질이니 어느
> 정의로 쟀는지 반드시 적으라」고 한다. 같은 규율을 **룰 선택 축**에는 적용하지
> 않고 있었다 — 이 검증 문서를 쓰다가 발견했고, 지금은
> `tests/docs/test_consistency.py` 가 귀속 없는 편차 주장을 막는다.

### 다른 손잡이도 같은 방식으로 돌아간다

```bash
uv run codeproof measure --analyzers ruff --slack 5 --store none   # 매칭 여유
uv run codeproof decoy stats --ruff-select F                       # 미끼 물림율
```

`measure` 출력의 `[매칭 민감도]` 는 slack 을 스윕해 **판정이 흔들리는지**를 같이
낸다. 흔들리면 그 결론은 매칭 정책의 산물이지 리뷰어의 성질이 아니다.

## T3 — 가드 반증 ⭐ (1분 · [실측 · 가드 28개 · 57초])

```bash
./scripts/falsify.sh
```

**테스트가 통과하는 것은 「가드가 있다」의 증거가 아니다.** 지키려는 것을
깨뜨렸는데도 통과하면 그 가드는 없는 것과 같다.

이 스크립트는 불변식을 하나씩 **일부러 깨고**, 해당 가드가 **실패하는지** 본다.
가드가 침묵하면 그게 실패로 보고된다. 끝나면 `git checkout` 으로 전부 되돌린다.

```
─── convention ───
  주장 : 관례 주장(docstring 누락)을 FP 로 세지 않는다 — F4a
  결과 : 가드가 울었다 (exit=1)
         회귀 상태의 provable_safety FP: 78건 (고친 상태는 한 자릿수다)
```

시나리오 목록은 `./scripts/falsify.sh --list` 로 본다. 하나만 돌리려면
이름을 준다(`./scripts/falsify.sh convention`).

> ⚠ **작업 트리가 깨끗해야 돈다.** 소스를 고쳤다 되돌리므로, 커밋 안 된 변경이
> 있으면 거부한다. 그 되돌리기가 당신의 변경을 지우기 때문이다.

### 왜 이게 필요했는가

문서 감사 중에 **가드 두 개가 공허했다.** 산문-생성물 대조 정규식이 FP 열이
아니라 TP 열을 읽고 있었고, 패키지 트리 검사는 문서 전체에서 이름을 찾아
트리에서 모듈을 지워도 통과했다. **둘 다 일부러 깨뜨려 보고서야 드러났다.**

손으로 했기 때문에 체계가 없었다. 이 스크립트가 그걸 반복 가능하게 만든다 —
그리고 아이디어는 새것이 아니다. 쌍마다 있는 `corpus/decoys/*/proof.py` 가
decoy 의 안전 주장을 공격으로 반증하듯, 이건 **가드의 주장**을 위반으로
반증한다. 한 층 위에 같은 구조를 올린 것이다.

| | 무엇을 반증하나 | 계약 |
|---|---|---|
| `proof.py` | decoy 의 「여기 결함이 없다」 | `attack(decoy)` 는 False **그리고** `attack(twin)` 은 True |
| `falsify.sh` | 가드의 「이 위반을 잡는다」 | 깨끗한 트리에서 통과 **그리고** 깨뜨리면 실패 |

🔴 **양쪽 다 두 줄인 이유가 같다.** 한 줄만으로는 무능한 검사가 통과한다.

`proof.py` 에 두 번째 줄이 없으면 `return False` 만 적어도 통과한다. 그리고
`falsify.sh` 도 처음엔 한 줄이었다 — **가드 테스트 파일을 이름만 바꿔도**
`pytest` 가 `exit=4`(file not found)를 내고 스크립트가 그걸 「가드가 울었다」로
읽어 **통과**했다. 가드가 통째로 사라졌는데 초록불이 켜지는 것이다.

[실측] 옛 버전으로 재현했다 — 가드 파일을 지운 채 돌리면 `가드가 울었다
(exit=4)` 를 내고 `exit=0`. 사전 검사를 넣은 지금은 `깨끗한 트리에서도 운다 —
가드가 고장났거나 시나리오가 낡았다` 로 보고하고 `exit=1` 이다.

**스크립트 자체가 공허한지도 확인할 수 있다** — 깨는 패턴이 낡아 아무것도 바꾸지
못한 시나리오는 `깨뜨리지 못했다 — 바꾼 곳이 없다` 로, 실제로 깼는데 가드가 통과하면
`가드가 침묵했다` 로 보고하고 둘 다 `exit=1` 이다. 앞의 것이 없을 때는 낡은 시나리오가
「공허한 가드」로 잘못 보고됐다 — 겨누던 줄을 고치자 두 시나리오가 그렇게 침묵했다.

## T4 — 코퍼스 라벨을 의심한다 (10분)

여기가 이 프로젝트의 급소다. **「증명된 음성」 라벨이 거짓이면 헤드라인이
통째로 무의미해진다** — 맞는 지적을 오답으로 채점하게 되기 때문이다.

```bash
uv run codeproof decoy validate --strict   # 형식 13종
uv run pytest tests/corpus/test_proofs.py  # 근거가 참인지
uv run pytest tests/corpus/test_mutants.py # 증명이 그럴듯한 약화를 깨고 안전한 변형은 통과시키는지
```

**두 줄이 보는 것이 다르다.** 첫 줄은 형식만 본다 — 근거가 60자 이상인가,
가드 심볼이 파일 안에 있는가. 근거가 **참인지**는 못 본다.

실제로 당했다. `D015` 의 가드로 `threading.Semaphore(4)` 를 썼는데, 세마포어 4는
스레드 4개를 동시에 들여보내므로 경쟁이 **실재했다.** 「증명된 음성」이라고
라벨링한 코드에 진짜 결함이 있었고, **형식 규칙 11개를 전부 통과했다.**

그래서 쌍마다 `proof.py` 가 있다. 계약은 두 줄이다:

```python
attack(decoy) is False   # 안전 근거가 참이다
attack(twin)  is True    # 🔴 공격이 실제로 결함을 잡을 수 있다
```

**두 번째 줄이 핵심이다.** 없으면 `return False` 만 적어도 통과한다 — 공격의
능력을 twin 으로 증명하게 만든 것이다.

### 당신이 직접 해 볼 것

decoy 하나를 골라 **공격을 강화해 보라.** 안전 근거가 거짓이면 `attack(decoy)`
가 True 가 되고 테스트가 깨진다.

```bash
ls corpus/decoys/ | head
cat corpus/decoys/D003-caller-held-lock/meta.toml    # 안전 근거를 읽는다
cat corpus/decoys/D003-caller-held-lock/proof.py     # 내가 쓴 공격
# proof.py 의 attack() 을 더 세게 고친 뒤:
uv run pytest tests/corpus/test_proofs.py -k D003
```

**여기서 하나라도 깨뜨리면 그건 이 프로젝트의 실패가 아니라 이 설계의 성공이다** —
검증 가능하게 만들어 놨기 때문에 당신이 깨뜨릴 수 있는 것이다. 다만 그 decoy 는
코퍼스에서 빠져야 한다.

> ⚠ 이건 **증명이 아니라 반증 시도**다. `attack` 이 False 인 것은 「아직 못 깼다」
> 이지 「깰 수 없다」가 아니다. 경쟁처럼 비결정적인 결함은 `ATTEMPTS = N` 을
> 선언해 양쪽 다 N회 시도한다 — decoy 는 **한 번이라도** 깨지면 실패이므로
> 시도를 늘리는 것이 완화가 아니라 강화다.

## T5 — 재현성 (선택 · 3분)

```bash
uv run codeproof measure --analyzers ruff --ruff-select ALL   # 저장한다
uv run codeproof measure --analyzers ruff --ruff-select ALL   # 한 번 더
uv run codeproof history --limit 5
uv run codeproof history --repro <위에서 알려주는 config-hash>
```

`config_hash` 는 **설정만** 담고 시각을 뺀다. 그래서 같은 해시끼리 결과를
비교하면 그게 재현성 검사가 된다. 정적분석기는 결정적이므로 달라지면 도구·환경
드리프트이고, 모델은 달라지는 것이 정상이며 **그 폭이 측정 대상**이다.

> 저장소는 `runs.db` 이고 git 에 올리지 않는다. 새로 받은 클론에는 이력이 없으니
> 위처럼 두 번 돌려야 비교할 것이 생긴다.

## T6 — 에이전트 층을 다시 채점한다 (API 키 불필요 · 선택 · 1분)

모델 숫자도 자격증명 없이 **다시 채점**된다. `claude-code` · `codex-cli` 를 목표 150쌍에서 샘플당 3회 돌린
**원본 지적**이 `results/agent/claude-code-neutral/` · `results/agent/codex-cli-neutral/` 에 실려 있다 —
`RUN.json`(모델 · effort · 격리 · 프롬프트 해시 · 잰 샘플과 그 코드의 지문)과 `findings.jsonl`(샘플 · 회차마다 한 줄).

```bash
uv run codeproof report --check                                                  # 다시 채점해 생성물과 대조
uv run codeproof report --out - | sed -n '/^## 에이전트 층/,/^## 이 숫자를/p'   # 그 절만 본다
```

`report` 는 리뷰를 다시 돌리지 않는다 — 실린 지적을 **채점만** 다시 한다. 그래서
검증되는 것은 채점과 집계이고, 모델이 같은 지적을 다시 낼지는 아니다(F8).
묶음을 빼고 대조하면(`--agents` 에 없는 경로) `exit=1` 이다 — 그 절이 생성물과
실제로 대조된다는 뜻이다.

확인할 것:

- 3회를 합집합 한 줄로 접지 않는다 — **단일 실행 기대값**과 **k-임계**가 다른 숫자로 나란히 선다
- **실행별 P-C** 의 폭이 같이 나온다 — 같은 설정의 모델 실행은 흔들린다
- slack 을 바꾸면 판정이 흔들린다고 **표가 스스로 말한다** (T2 의 손잡이가 여기서도 돈다)

[실측 · claude n=8 · 60쌍] 원본 지적이 실려 있어서 발표한 숫자의 오류를 잡았다 (그 묶음은 지금 `results/agent-archive/claude-code/`). `paired_fix`
의 단일 실행 기대값이 60.4% 로 실렸는데, 같은 지적을 회차마다 단독으로 다시 채점한 평균은 62.7% 였다.
짝의 지적을 받는 채점자에 **합집합 짝**을 넘기고 판정만 관점으로 걸러낸 버그였다.
지금은 관점마다 다시 채점하고, `./scripts/falsify.sh view-regrade` 가 그 가드를
깨뜨려 본다.

## 면접관용 — 이 프로젝트를 떨어뜨리는 질문

각 질문에 **어디를 보면 답이 나오는지**를 같이 적었다. 답이 마음에 안 들면
그게 이 프로젝트의 한계이고, 대부분은 문서가 먼저 그렇게 적고 있다.

| # | 질문 | 어디를 보나 |
|---|---|---|
| 1 | **decoy 를 직접 썼으면 자기 유리하게 쓴 것 아닌가?** | `proof.py` 가 근거를 실행으로 반증한다. D015 사례가 형식 규칙 11개를 통과하고도 거짓이었다 — 그래서 실행 층을 추가했다. T4 |
| 2 | **이 표본으로 무엇을 말할 수 있나?** | 말할 수 없다고 도구가 **실행마다 스스로 경고**한다(`credibility_warning`). 「측정 선택이 숫자를 움직인다」에는 충분하고 「이 도구의 오탐률은 X%」에는 부족하다 — 다른 주장이고 다른 표본이 든다 |
| 3 | **정적분석기 숫자 아닌가? 모델은?** | 헤드라인은 그렇다. 에이전트 층(`claude-code` · `codex-cli` · 목표 150쌍 · 샘플당 3회)은 원본 지적이 실려 있어 **자격증명 없이 다시 채점**된다 — T6. 모델 API 층은 아직 싣지 않았고, `ReviewerKind` 가 다르면 **섞어 집계하지 않는다**. 정적분석기만으로는 이 코퍼스의 시험률이 낮다 — 린터는 위험 API 와 타입 오류만 본다 |
| 4 | **34배[실측 · 60쌍]는 체리피킹 아닌가?** | **부분적으로 맞다.** `S` 에서는 편차가 사라진다. 그 사실을 README 결과 6 과 T2 에 내가 먼저 적었고, 귀속 없는 편차 주장은 테스트가 막는다 |
| 5 | **테스트가 다 통과한다는 게 무슨 의미인가?** | 그것만으로는 의미 없다. `scripts/falsify.sh` 가 가드를 깨뜨려 본다. 실제로 공허한 가드 두 개를 그렇게 잡았다. T3 |
| 6 | **틀린 적 있나?** | 있다. 발표한 결론 **두 개를 철회**했다(미끼 시험률 · 가드 위치 순서). 관례 주장을 오탐으로 세던 버그였고 노이즈가 신호처럼 보였다. README 결과 3 에 철회 기록이 남아 있다 |
| 7 | **그래서 이게 왜 쓸모있나?** | 같은 과제에 발표된 Precision 이 문헌마다 20배 차이 나는데[소스: README 참고문헌] 아무도 그 편차를 재지 않았다. 이건 **도구 순위표가 아니라 순위표를 읽는 법**이다 |

### 되짚어 물으면 좋은 것

- 「`static_corroboration` 을 편차에서 왜 뺐나?」 → 뺀 이유를 설명하지 못하면
  **0 → 238 로 부풀릴 수 있었다.** 유리한 쪽으로 안 쓴 자리다.
- 「판정 불가를 FP 로 접으면 안 되는 이유는?」 → 기존 문헌이 여기서 틀렸다.
  증거의 부재를 오답으로 채점하면 사람이 놓친 버그가 FP 가 된다.
- 「`--ruff-select S` 에서 편차가 사라진다면 헤드라인은 무의미한 것 아닌가?」
  → **가장 날카로운 질문이다.** 답: 헤드라인이 좁아질 뿐 방향은 유지된다.
  「정의가 중요하다」가 아니라 「정의가 중요한지조차 설정에 달려 있다」로 읽으면
  논지가 더 강해진다 — 측정 선택이 **결론의 존재 여부**까지 정하기 때문이다.

## 이 프로토콜이 확인해 주지 **못하는** 것

적지 않으면 통과가 과신으로 읽힌다.

| 못 보는 것 | 왜 |
|---|---|
| **모델 리뷰의 재실행** | 새로 돌리려면 자격증명이 든다. T6 은 실린 지적을 다시 **채점**할 뿐 리뷰를 다시 돌리지 않는다 |
| **실제 PR 분포에서의 오탐률** | 손으로 쓴 decoy 다. 분포를 대표하지 않는다 |
| **안전 근거가 전부 참이라는 것** | 반증 **시도**다. 공격이 약하면 통과한다 |
| **사람 리뷰어와의 비교** | 사람 리뷰는 `Reviewer` 로 받을 수 있지만 표본이 없다 |
| **지연(latency)** | 정확도·비용과 같은 실험에서 재지 않는다 — batch 에 요청별 타이밍 필드가 없다 |
| **재현 가능한 *출력*** | Anthropic 에 `seed` 가 없다. 재현되는 것은 **프로토콜**이지 출력이 아니다 |
