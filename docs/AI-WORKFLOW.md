# AI 에이전트와 일하는 방식

> 이 저장소는 백엔드 개발자가 AI 에이전트와 일하다 생긴 질문에서 시작했고, 그 에이전트와 함께 만들었다.
> 무엇을 맡기고 무엇을 직접 정했는지, 에이전트와 쓴 코드가 어디서 조용히 틀렸고 무엇이 그것을 잡았는지를 적는다.

## 출발점 — 49라운드가 수렴하지 않았다

실무 Spring 프로덕션 레포(소스 2,800여 개)에서 Codex 와 Claude 를 매일 함께 쓴다. 세션마다 재주입되는 규칙 정본과
가드 훅으로 빌드 그린 · 문서 정합 · 규칙 무결성을 **사람이 아니라 하네스가** 막게 해 뒀다.

그 레포에서 PR 하나를 두고 **리뷰 봇과 49라운드**를 돌았다.

| 실측 | 값 |
|---|---:|
| 봇 인라인 지적 | **149건** |
| 그중 이 PR 의 산출물에 대한 것 | **7건 (4.7%)** |
| 나머지 | 도구에 대한 것 142건 (95%) |
| 「발생 근거」가 제시된 지적 | **0건** (기전 재현만 15건) |
| 그럼에도 반영한 수정 | **15건** |
| 내 방어가 다음 라운드 지적을 만든 횟수 | **2회** |
| 되돌리기 직전 파일의 주석 · 산문 비율 | **65%** |

**이 루프는 수렴하지 않았다.** 지적을 다 해소해서 끝난 게 아니라 **리뷰 대상 표면을 제거해서** 끝났다 —
2,212행을 331행으로 되돌렸다. 각 수정은 **하나씩 보면 옳았고 전체로 보면 틀렸다.** 오지 않는 상황을 막으려고
팀이 읽는 파일의 복잡도를 8배로 올렸다 [실측]. 그 비용은 리뷰에 나타나지 않는다.

> **`shellcheck` 가 깨끗해도 리뷰는 끝나지 않는다 — 층이 다르다.**
> 정적 분석기 통과를 「이제 깨끗하다」의 근거로 쓰지 않는다.

답할 수 없는 질문이 남았다 — **저 149건 중 무엇이 맞았는가? 무엇을 기준으로? 기준을 바꾸면 답이 바뀌지 않는가?**

공개된 벤치마크를 뒤져 보니 같은 과제 · 비슷한 도구인데 **발표된 Precision 이 20배 차이 난다** [소스: 아래 표 · 각 행의 링크].

| 벤치마크 | Precision | 정답의 정의 |
|---|---:|---|
| [CR-Bench](https://arxiv.org/abs/2603.11078) | ~3.5% | 사람이 실제로 남긴 리뷰 코멘트와 일치 |
| [SWRBench](https://arxiv.org/abs/2509.01494) | 16.65% | 〃 (균형 코퍼스) |
| [Martian](https://github.com/withmartian/code-review-benchmark) | 76.2% | 리뷰 후 개발자가 **실제로 고친 것**과 일치 |
| [Qodo](https://www.qodo.ai/blog/qodo-outperforms-claude-in-code-review-benchmark) (벤더 자체 벤치마크) | 79% | **주입한 결함**과 일치 (LLM 판정자로 채점) |

차이의 원인은 모델이 아니라 **「정답을 무엇으로 볼 것인가」**다. 그리고 **동일한 지적 집합을 여러 정답 정의에 통과시켜
그 편차를 발표한 사례가 없다.** 그래서 질문이 정해졌다.

> **「보고된 품질 숫자 중 얼마가 모델의 것이고, 얼마가 측정 선택의 것인가?」**

```
                    ┌─ Grader A ─┐
Finding[] (고정) ───┼─ Grader B ─┼──→ 같은 지적, 다른 Precision
   ↑                ├─ Grader C ─┤              ↓
Claude / Codex      └─ Grader D ─┘      편차 = 측정의 기여분
```

프롬프트 **포맷만** 바꿔도 정확도가 최대 **76 포인트** 움직인다는 보고가 이미 있다
([Sclar et al.](https://arxiv.org/abs/2310.11324)). 측정 설정의 기여분이 모델 차이를 압도할 수 있고,
코드리뷰에서는 아직 아무도 재지 않았다.

## 이 저장소를 만든 방식

PR 병합 커밋을 뺀 모든 커밋을 Claude Code 와 함께 썼다 [실측 · 2026-10-07 · `git log --no-merges` 의 공동 작성자 표시].

역할은 Claude Code 공식 best practice 에서 다섯 가지를 골라 나눴다 [소스: [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
— 「Give Claude a way to verify its work」 · 「Explore first, then plan, then code」 · 「Configure your environment」(훅 · 권한) ·
「Automate and scale」(적대적 검토 단계)].

| 원칙 | 사람이 한다 | 에이전트가 한다 | 이 저장소의 장치 |
|---|---|---|---|
| 스스로 돌릴 확인 수단을 준다 | 무엇이 통과인지 정한다 (예: 받아서 바로 돌아가야 한다) | 확인을 돌리고 증거를 보인다 | 테스트 · [`falsify.sh`](../scripts/falsify.sh) · [`verify.sh`](../scripts/verify.sh) · 산문의 `[실측]` 표시 |
| 탐색 → 계획 → 구현 | 계획을 승인한다 — 측정 절차 · 반복 횟수 · 멈춤 규칙은 데이터를 보기 **전에** | 탐색 · 계획 초안 · 구현 · 선언대로 실행 | 측정 선언을 먼저 커밋하고, 실행기가 선언과 다른 설정을 거부한다 |
| 꼭 지켜야 하는 것은 코드로 강제한다 | 무엇을 강제할지 승인한다 | 규칙 안에서 일한다 | 편집 훅 · 아키텍처 테스트 (아래) |
| 권한을 좁힌다 | 밖으로 나가거나 되돌릴 수 없는 일 — push · 병합 · 유료 실행 · 삭제 | 그 밖의 판단은 근거를 남기고 진행 | 측정 대상 에이전트는 권한 프로필 · 격리 설정 안에서 돈다 |
| 쓴 쪽이 채점하지 않는다 | 검증 보고와 CI 를 보고 받아들인다 | 다른 문맥의 독립 검토 · 다른 패밀리(Codex)의 라벨 감사 | [DESIGN §3.5](DESIGN.md) 라운드 기록 · [DESIGN §9](DESIGN.md) 의 5 |

**규칙은 문서가 아니라 코드로 지킨다.** [CLAUDE.md](../CLAUDE.md) 는 세션마다 에이전트에게 다시 읽히는 작업 규칙이다.
그런데 문서에만 적은 규칙은 지켜지지 않았다 — 「`cli.py` 는 구현체를 직접 만들지 않는다」고 적어 둔 동안 실제로는
8곳에서 직접 만들고 있었다 (DESIGN 교훈 #23). 그래서 규칙을 아키텍처 테스트 · 편집 훅 · 반증 시나리오로 강제한다.
규칙이 생긴 실패와 바꾼 것은 [DESIGN §12](DESIGN.md) 의 교훈 표에 있다.

**확신도를 표시한다.** 산문의 사실 주장에는 `[실측]`(직접 실행 · 조회) · `[소스]`(문서 · 코드 인용) · `[추정]` 중 하나를
붙이고, 숫자에는 표본 크기를 붙인다 (`[실측 · 150쌍]`) — 숫자와 표본이 붙어 다니면 스스로 날짜를 밝힌다. `[실측]` 은
관측값에만 붙이고 그 해석에는 붙이지 않는다.

## 에이전트와 쓴 코드가 조용히 틀린 자리

모두 예외도 경고도 없었다.

| 무엇이 틀렸나 | 지금 무엇이 막나 | 기록 |
|---|---|---|
| 실행 경로가 셋으로 갈라져 새 채점 훅이 한 경로에만 걸렸다 — 나머지 둘은 짝 채점을 **전부 TP** 로 기록했다 | 경로를 `run_reviewer` 하나로 합치고 아키텍처 테스트로 고정 | DESIGN 교훈 #26 |
| 매니페스트가 `strict=False` 라고 적는 동안 mypy 는 이 저장소의 `strict = true` 를 주워 와 돌고 있었다 | 측정 도구를 호스트 설정 · 캐시에서 격리 | DESIGN 교훈 #19 |
| 가져오기 파서가 버린 지적을 세지 않았다 — 경로가 다른 SARIF 가 exit 0 · 경고 0 · 「지적 0건」으로 들어왔다 | 포맷마다 버린 지적과 이유를 센다 | DESIGN 교훈 #39 |
| 테스트가 통과하는데 가드는 없었다 — 문서 대조 테스트 둘이 공허했다 | 불변식을 일부러 깨고 테스트가 우는지 보는 [`falsify.sh`](../scripts/falsify.sh) | [VERIFY.md](VERIFY.md) T3 |
| 그 `falsify.sh` 가 목록만 보려던 명령에서 커밋 안 된 작업을 지웠다 | 되돌리기는 깨끗한 트리를 확인한 뒤에만 건다 | `falsify.sh` 주석 |
| 발표한 결과가 틀렸다 — `provable_safety` 의 「구별 성공 11/60」이 전부 스타일 지적이 결함 줄에 우연히 겹친 것이었다 [실측 · 60쌍 시점] | 철회하고 기록을 남겼다 · 양쪽에 같은 경계를 둔다 | DESIGN 교훈 #47 · [RESULTS.md](RESULTS.md) 결과 3 |

## 측정 대상인 에이전트에도 같은 원칙을 건다

- 에이전트 CLI 는 개인 설정을 싣고 돈다. 첫 전체 측정이 네 군데서 조용히 틀렸고, 그중 둘은 개인 설정(effort · 전역 규칙 ·
  훅 · MCP)이 측정 조건으로 실린 것이었다 → CLI 를 호스트 설정에서 격리하고 모델 · effort · 판을 실행마다 기록한다
  ([DESIGN §7.10](DESIGN.md)).
- Codex 에게 쌍을 쓰게 하는 실험([DESIGN §7.10d](DESIGN.md))에서는 권한 프로필로 저장소 · 홈을 막고, 막혔는지를 모델을
  부르기 전에 점검하고, 첫 호출의 이벤트에서 다시 확인한다. 그 과정에서 CLI 플래그 하나가 권한 프로필을 오류 없이 덮어쓰는
  것을 찾았고, 저자가 읽을 수 있는 하네스 소스에 claude 쌍의 흔적이 남아 있던 것도 찾아 지웠다.
- 주 지표에 LLM 판정자를 쓰지 않는다 — 자기선호 편향이 Claude vs Codex 비교를 무효화한다 ([RESULTS.md](RESULTS.md)).
